## The one-line version

The simulator now models the sensors the bike will actually have — the onboard
velocity estimate, encoder quantisation, and the TM151's attitude error — and
that turned out to be the largest untested sim-to-real gap in the project. A
policy trained on MuJoCo truth survives **0.15** of the eval grid on the real
velocity estimate and **0.20** with a TM151 attitude, against 1.00 on truth.
`general_rl_odo_ahrs`, trained against both, holds **1.00**.

## First task, if you want one — price the TM171

Small, ~2 minutes of compute, and it answers a purchasing question nobody can
answer from the datasheet. Run it before reading everything else; it will also
teach you the eval tooling.

```sh
python analysis/chatter.py --policies general_rl_odo_ahrs \
    --encoder counts --ahrs tm151          # baseline: 0.672 / surv 1.00
python analysis/chatter.py --policies general_rl_odo_ahrs \
    --encoder counts --ahrs tm171          # the number that is missing
```

**The question.** Is the TM151 the bottleneck, or was training against it
enough? `general_rl_odo_ahrs` already holds survival 1.00 on the TM151, so a
better part cannot improve survival — it can only improve `track_geo`,
`vel_err` and `head_err`. If those barely move, **the part is not worth
buying**, and that is a real result: it would say the fix for sensor error was
training against it, not spending money.

**Why it is not already known.** The existing TM171 row (0.689 against 0.537)
was measured on `general_rl_odo`, which never trained against an AHRS at all.
That prices the part for a policy caught unprepared. This prices it for the
policy we would actually fly.

**Run it at BOTH taus**, because `odo_ahrs` is specialised to 2.0:

```sh
python analysis/chatter.py --policies general_rl_odo_ahrs \
    --encoder counts --ahrs tm171 --ahrs-tau 0.19
```

If the TM171 advantage survives at the measured tau, it is real. If it only
shows at 2.0, it is an artefact of the training constant and should not be
believed — see the trap section.

**What `tm171` actually changes** (measured by ablation, do not re-derive):
orientation RMS 1.5° → 1.0° carries essentially all of it. Yaw drift and
misalignment do nothing. So this is a one-parameter question wearing a
part-number label.

Record the result in `docs/status.md` next to the other sensor tables.

## What is actually next

**In the order I would do it.**

1. **Point `control.general_move` at `general_rl_odo_ahrs`.** It is the only
   export that survives the sensors the bike will actually have. Repointing
   moves NEITHER digest and changes nothing in the test suite, both measured.

   `general_rl_smooth_diff_pi` stays as a **previous rev and a ceiling
   reference**, not a co-equal default — it answers "how much is on the table
   if the sensing were perfect", which is the same role `--ahrs tm171` plays
   for "if the part were better":

   | reference | score / surv | what it prices |
   |---|---|---|
   | `smooth_diff_pi` on truth | 0.808 / 1.00 | perfect sensing — the ceiling |
   | `odo_ahrs` at `--ahrs tm171` | — (unmeasured) | a better AHRS |
   | `odo_ahrs` at `--ahrs tm151` | 0.672 / 1.00 | **what we have** |

   So the ideal-sensor test mode in item 3 exists to MEASURE THE CEILING, not
   to support a second production path. Keep the number, retire the pointer.

   (Worth running the middle row — it is one `chatter.py` invocation and would
   say what a TM171 buys a policy that trained against a TM151.)

2. **Randomise the AHRS error PARAMETERS.** Note carefully what is and is not
   already randomised, because the distinction is the whole point:

   | | randomised? |
   |---|---|
   | error realisation — noise trajectory, misalignment draw, orientation walk | **yes**, fresh seed per episode |
   | the parameters — `ahrs_level` RMS, `ahrs_tau_s` | **no**, one fixed value every episode |
   | anything in `randomize.py` | it does not touch sensors at all |

   Every episode draws a different error from the SAME fixed distribution,
   which is exactly why `odo_ahrs` specialised to `tau=2.0`.

   **What range?** Not centred on the recorded values — those are RESTING
   figures (roll RMS 0.0142°, tau 0.19 s) and the bike does not rest. The
   datasheet's dynamic bound is 1.5°. That is a ~100x span with the true
   moving value unmeasured somewhere inside it, so log-uniform across the whole
   thing: roughly 0.05-2.0° and 0.1-3 s. The measurement's contribution is a
   defensible FLOOR, which did not exist before it.

   This is orthogonal to item 1: two policies answers *which distribution*, and
   randomising answers *how wide*. Doing only the first leaves policy B
   precisely calibrated to one guessed number.

3. **Split the tests into ideal-sensor and sim-sensor modes.** Agreed as the
   shape; the closed-loop bike test itself is DEFERRED. Conditions to record
   for it, in detail, since that is the point of deferring rather than dropping:

   - the assertion is SURVIVAL over the eval grid, not RMS against truth — an
     open-loop accuracy objective was measured selecting a WORSE estimator
   - ideal mode: truth sensors, `general_rl_smooth_diff_pi`, baseline 0.808/1.00
   - sensor mode: `--encoder counts --ahrs tm151`, `general_rl_odo_ahrs`,
     baseline 0.672/1.00 at tau 2.0 and 0.570/0.95 at tau 0.19
   - it must fail if a truth-trained policy is run in sensor mode: that is the
     0.808 → 0.044 collapse, and nothing currently catches it
   - marker would be `contact` (model build + rollouts, seconds not ms)
   - 20-command grid at 15 s is ~30 s serial; a 4-command subset is enough for
     a regression guard

4. **The 180° edge case, now reproduced and bounded.** Forward at 0.6 m/s for
   4 s, then flip the heading command; 6 s after; 6 seeds:

   | policy | AHRS | flip | falls |
   |---|---|---|---|
   | `general_rl_odo_ahrs` | tm151 | **180°** | **2/6**, at t+0.6 s |
   | `general_rl_odo_ahrs` | tm151 | 90° | 0/6 |
   | `general_rl_odo_ahrs` | none | 180° | 0/6 |
   | `general_rl_odo` | tm151 | 180° | 3/6 |
   | `general_rl_odo` | none | 180° | 0/6 |

   **It needs the AHRS error** — every no-AHRS row is clean. `odo_ahrs` is
   better than `odo` (2/6 vs 3/6) but does not fix it.

   **It is NOT a 180° branch point.** That was the obvious hypothesis — ±180°
   is where the heading error's sign is ambiguous, so noise could flicker the
   turn direction — and the sweep refutes it:

   | flip | 150° | 170° | 179° | 180° | 181° | 190° | 210° |
   |---|---|---|---|---|---|---|---|
   | falls | 1/6 | 2/6 | 2/6 | 2/6 | 2/6 | 2/6 | 1/6 |

   No spike at 180, and 179 and 181 are identical to it. So it is simply the
   SIZE of the commanded heading change: flat and bad above ~170°, easing by
   150°, clean by 90°. Whatever the mechanism, it is not a singularity, which
   rules out the cheap fix of special-casing the branch.

   Six seeds, so 1/6 against 2/6 is weak — the flatness across 170-190 is the
   part to trust, not the shape of the tails.

5. **Diagnose the physics/contact change that degraded the LQR.** Still open,
   and it predates all the sensor work. Nine of the 23 red tests are the
   analytic LQR; `q_steer` 0.5 → 5.0 and `q_roll_rate` 6.0 → 30.0 recovered it
   enough to pass `test_balance`, but WHY the contact change cost that much was
   never established. The contact model remains the least-measured parameter in
   the sim and the one no policy has been randomised over.

## Traps, and things not to re-derive

**THE BIG ONE: a policy trained against a single fixed value of an unmeasured
constant specialises to it, and the eval cannot reveal that unless the constant
is varied.** `general_rl_odo_ahrs` trained at `ahrs_tau_s` 2.0; the real part
measures 0.19; at the real value it gives back half its gain (1.00 → 0.95
survival). I had earlier claimed the tau guess "changed nothing" — true for
`general_rl_odo`, which never trained against the AHRS, and false for the
policy that did. Do not trust a flat sweep run on a policy that did not train
on the parameter.

**`TAU_ORIENT_S` is deliberately still 2.0 and is a TRAINING CONTRACT, not a
best estimate.** Changing it silently reprices `odo_ahrs`. Pass `tau_orient_s`
to evaluate at the measured 0.19.

**Sensor constants live in `sim_ahrs.py` / `sim_odometry.py`, not in
`bike_params.yaml`** — on purpose. `plant_digest` hashes every top-level key
except `control`, so putting them in the config would invalidate all eight
digest-matching exports for a change that does not move the bike. Measured:
`e1ec36bfa670217e → 5f270674e21c3edc`.

**Replay needs the flags.** `--odometry --odometry-encoder counts --ahrs tm151
--general general_rl_odo_ahrs`. Teleop warns in both directions now (policy
trained on sensors and run without; sensors on and the policy never trained on
them), because the mismatch looks like a broken policy and is not.

**The mount question is not answered.** The gyro is mount-independent exactly
(machine precision, and a real result); the accelerometer's lever arm is linear
in the arm at ~0.070 m/s² per mm from the CoM, and the as-built position is
already the best realisable one. But `sim_ahrs` applies its orientation RMS
regardless of position, so a flat eval across mounts proves nothing. The
chassis origin is NOT a mounting position — it is the rear axle centre, inside
the wheel.

**The desk measurements are best-case.** One unit, room temperature, dead
still. Roll RMS 0.0142° against a 0.5° model is not licence to lower the model,
and says nothing about the DYNAMIC figure, which is what every sensor result
turns on. The gyro reading 0.575 p-p against a ≤0.5 spec is probably building
vibration, not the part — re-measure on foam before believing it.

## Corrections I made to my own claims this session

Recorded so they are not re-derived, and because each was wrong in a way that
looked right:

- "The tau guess changed nothing" — false for the policy that trained on it.
- "Repointing `general_move` moves `design_digest`" — false since the
  plant/design split; it moves neither. This had propagated into a commit
  message and two docs.
- "The odometry seven are a separate problem from the LQR" — 4 of 7 are the
  estimator, 3 are artifacts of a fixture that drives the LQR. 14 of the 17
  tests in that file ride on it.
- "Pull the tan coefficient first, a geometry constant is off" — the geometry
  is fine; the fit's regressors are 98% collinear under the LQR and recover
  0.968 under RL. That advice was chasing a conditioning artifact.
- "The 40x aliasing margin licenses plain subtraction" — backwards. It licenses
  an unwrap; it does not remove the need for one. The hubs really do wrap.
