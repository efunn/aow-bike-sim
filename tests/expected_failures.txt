# THE ANALYTIC LQR DRIVE CONTROLLER, nine cases. Registered 2026-08-25.
#
# ACCEPTED because the cause is known and the controller is not what drives the
# bike. RL is primary; the LQR is the reference baseline, kept for comparison
# and to be tried on hardware later. It is simply not good enough yet, and
# nobody is tuning it this week.
#
# What it CAN do, driven by hand in teleop: spawn without falling or
# oscillating (that much was fixed by q_steer 5.0 / q_roll_rate 30.0), drive
# forward at low speed, reverse barely, and pivot cleanly. What it cannot do is
# hold a turn or reach v_max upright.
#
# The suite agrees with the hand test, which is why these are priced rather
# than merely observed:
#   - straight_sprint[-0.5] does NOT fall (max roll 6.08 deg). It just tracks
#     badly: cruise -0.322 against a -0.5 target. That IS "reverses barely".
#   - straight_sprint[0.8] and all four command_heading cases DO fall, 180 deg.
#   - test_pivot.py passes entirely, matching "it pivots ok".
#   - test_balance.py [lqr] passes, matching "does not fall over on spawn".
#
# test_hold_ramps_to_full_speed_with_auto_repeat is the cleanest reproduction:
# it tracks the ramp to v_max upright (1.173 of 1.20 at t=1.25 s, roll inside
# 1.1 deg) and then tips at about t=1.4 s. Start there.
#
# THE FIX IS A BETTER LQR, not a looser assertion and not an easier plant. An
# earlier suggestion to point these at a reduced-difficulty bike_params was
# rejected: the command and actuation path is already proven working by that
# first 1.25 s, so an easier plant would hide the fall rather than isolate
# anything.
